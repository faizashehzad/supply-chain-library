# Project Context: Supply Chain Logistics Library

## Overview
A Java-based logistics library demonstrating modularity and clean architecture.

## Technical Stack
- **Language**: Java.
- **Libraries**: Java Standard Library, Google Guava, and Apache Commons are allowed.
- **Specification**: All core code should be specifiable using **JML (Java Modeling Language)**
                     based on Deductive Software Verification – The KeY BookKeY Book.

## Design Goals
- **Design Patterns**: The project must implement 2 to 3 design patterns (e.g., Strategy, Observer).
- **OOP Principles**: Use inheritance and polymorphism where appropriate to model the domain.
- **Structure**: Maintain clear separation between models, core logic, and observers.

## Domain Mapping (Real-World Analogy)
- **Warehouse Class**: Represents a **Cross-Docking Facility** or **Parcel Sortation Hub** (e.g., a FedEx/UPS hub).
  - It does NOT store raw product inventory.
  - It handles **Shipments** that are in transit.
  - `inventory` represents packages currently on the sorting floor or in staging lanes.
- **Location Class**: Represents a physical point in the supply chain (e.g., a city, a specific address, or a facility).
- **Shipment Class**: Represents a finalized, labeled package or pallet ready for transport.
- **Route Class**: Represents a predefined path or sequence of facilities a shipment will travel through.
- **ShipmentProcessor**: Represents the facility's sorting and loading operations.
- **Observers**: Represents the automated tracking and logging systems (TMS) within the hub.
**Global Restrictions:**
- **Enums are out of scope and shall not be used.**
- **Distances must be `long` typed, avoiding `float` or `double`.**

## JML Representation of Collections (using Ghost Fields)

For classes that internally manage collections (like `java.util.List` or `java.util.ArrayList`),
ML specifications may use **ghost fields** to represent the abstract state of these collections.
This allows for formal reasoning without exposing internal implementation details.

**Key Concepts:**
- **`ghost` fields**: These are specification-only fields that do not exist in the compiled Java code. They are used to model abstract properties of the object's state.
- **JML Sequence (`\seq`)**: This is a built-in JML model type that represents a mathematical sequence. It is ideal for modeling ordered collections like `List`s.
- **`content` ghost field**: A common convention is to use a `ghost \seq<E> content;` field to represent the elements of a collection.

**Supported JML Sequence Functions (KeY Extension):**
- `\seq_get(s, idx)`: Returns the element at index `idx` in sequence `s`.
- `s.length`: Returns the integer size (length) of sequence `s`. (Corrected from `s.int_size()`).
- `\seq_concat(s1, s2)`: Returns a new sequence that is the concatenation of `s1` and `s2`.
- `\array2seq(array)`: Converts a Java array to a JML sequence.
- `\seq_def(type, low, high, func)`: Defines a sequence where elements are generated by `func` from `low` to `high`.
- `\seq_sub(s, start, length)`: Returns a subsequence of `s` starting at `start` with `length`.
- `\seq_empty`: Represents an empty sequence.
- `\seq_reverse(s)`: Returns a new sequence with the elements of `s` in reverse order.
- `\seq_singleton(e)`: Returns a new sequence containing only the element `e`.

**Example Usage (Conceptual for `List<E>`):**
```java
public interface List<E> {
    //@ public ghost \seq<E> content; // Represents the abstract sequence of elements

    //@ public invariant content != null; // The model sequence itself is never null
    //@ public invariant content.length == size(); // The size of the model sequence matches the size() method (Corrected to .length)

    /*@ public normal_behavior
      @ ensures \result == content.length; // Corrected to .length
      @ assignable \strictly_nothing;
     */
    int size();

    /*@ public normal_behavior
      @ requires var1 != null;
      @ ensures content == \seq_concat(\old(content), \seq_singleton(var1)); // Appends element to the sequence
      @ ensures \result == true;
      @ assignable content;
     */
    boolean add(E var1);

    /*@ public normal_behavior
      @ requires 0 <= var1 && var1 < content.length; // Corrected to .length
      @ ensures \result == \old(content.get(var1)); // Returns the element at index
      @ ensures content == \old(content).remove(var1); // Removes element from the sequence
      @ assignable content;
     */
    E remove(int var1);
}
```
This approach ensures that JML specifications for collection-based classes are precise, verifiable, and consistent with the project's formal methods goals.
